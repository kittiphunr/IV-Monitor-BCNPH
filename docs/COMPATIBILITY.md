## ชั้นที่ 1 โครงสร้างแพ็กเก็ต

`bash tools/protocol-test/run.sh` เทียบ `struct_message` (23 ไบต์) และ `struct_host_sync` (20 ไบต์)
ทีละฟิลด์ทั้งชนิดและชื่อ ตรงกันทุกเฟิร์มแวร์

## ชั้นที่ 2 ความหมายของค่า

อ่านจากซอร์สของทุกสายแล้วเทียบกัน

| หัวข้อ | ผล |
|---|---|
| รหัสเตือน 0 ถึง 5 | ตรงกันทุกสาย |
| รหัส 6 `NO_SIGNAL` และ 7 `LOST_LINK` | มีเฉพาะฝั่ง Host ทุก Host แปลงเป็น 0 ก่อนส่งให้ Station (`alertCodeForStation()`) |
| บิตใน `struct_host_sync.flags` | 0x01 รับทราบใกล้หมด · 0x02 Host ได้ยินเตียงนี้ · 0x04 Host รายงานบิต 0x02 ตรงกันทั้ง 3 Host และ 4 Station |
| บิตใน `struct_message.flags` | 0x01 พยาบาลกดรับทราบใกล้หมดที่เตียง ตรงกันทุกสาย |
| `msSinceLastDrop` | 0 = ยังไม่มีหยด ทุก Station ส่งอย่างน้อย 1 เมื่อมีหยดแล้ว (C3 แก้ในรอบนี้) |
| เลขเตียง | Station ตั้งได้ 1 ถึง 8 Host รับ 1 ถึง `MAX_SUPPORTED_STATIONS` = 8 ตรงกัน |
| แรงดันแบตเตอรี่ | Station ส่งไม่เกิน 4.2 V (หรือ 0 ถ้าไม่มีวงจรวัด) Host รับถึง 6 V |
| อัตราไหล | **ไม่เข้ากันก่อนแก้** ดูหัวข้อ "สิ่งที่แก้" ข้อ 1 |
| `resetSeq` (เริ่มถุงใหม่) | **C3 ไม่เข้ากันก่อนแก้** ดูหัวข้อ "สิ่งที่แก้" ข้อ 2 |
| `safeDropFactor()` / `safeNearPct()` | เหมือนกันทุกไบต์ ยกเว้น C3 ที่รับช่วงกว้างกว่า (DF 10 ถึง 60, ใกล้หมด 10 ถึง 99%) Host ส่งเฉพาะค่าในช่วงแคบอยู่แล้ว จึงไม่มีผล |
| สูตรเกณฑ์ NO FLOW | Host ทั้งสามเหมือนกันทุกไบต์ และตรงกับ Station / Stable / Fallout · C3 คำนวณจากช่วงห่างที่วัดได้จริง ใช้แค่แสดงบนจอของตัวเอง เสียงเตือนตัดสินที่ Host แล้วส่งรหัสมาให้ C3 แสดงเหมือนสายอื่น |

## ชั้นที่ 3 ทดสอบไขว้ด้วยโค้ดตัวจริงทั้งสองฝั่ง

`bash tools/compat-test/run.sh` สร้างเฟิร์มแวร์ทั้ง 7 สายบน PC แล้วทำสามขั้นต่อหนึ่งคู่

1. Station ตัวจริงเล่นฉาก (หยดผ่าน `onDropDetected()` และ `loop()` ตัวจริง) เก็บทุกไบต์ที่ส่งออก
2. Host ตัวจริงรับไบต์เหล่านั้นผ่าน `OnDataRecv()` ตัดสินสัญญาณเตือนเอง แล้วเก็บ Sync ที่ส่งกลับ
3. Station ตัวจริงรับ Sync ตัวจริงของ Host นั้น แล้วดูว่าเข้าใจตรงกันไหม

| ฉาก | สิ่งที่ต้องเป็น | ก่อนแก้ | หลังแก้ |
|---|---|---|---|
| normal ไหลปกติ 100 mL/h | ไม่มีเตือน ทั้งสองฝั่งเห็นกัน ค่าตั้งตรงกัน | 12/12 | 12/12 |
| fast ไหลอิสระ 3600 mL/h (DF10) | TOO FAST ทั้งสองฝั่ง | **0/12** | 12/12 |
| maxrate หยดห่าง 70 ms (5143 mL/h) | TOO FAST ทั้งสองฝั่ง | **0/12** | 12/12 |
| nearend เกิน 80% ของแผน | NEAR END ทั้งสองฝั่ง | 12/12 | 12/12 |
| reboot บูตใหม่ ขณะ Host มี resetSeq = 3 | ยอดหยดที่กู้คืนไม่ถูกล้าง | **3/4** (C3 เหลือ 6 จาก 12400) | 4/4 |
| newbag กดเริ่มถุงใหม่กลางฉาก | ตัวนับเริ่มใหม่จริง | 4/4 | 4/4 |
| slowdown หมุนตัวปรับหยดช้าลง 4 เท่า | จอเตียงขึ้น 25 mL/h ทันทีหลังช่วงแรก | **0/4** (ค้าง 100 หรือขึ้น 0) | 4/4 |
| speedup หมุนตัวปรับหยดเร็วขึ้น 4 เท่า | จอเตียงขึ้น 400 mL/h ทันทีหลังช่วงแรก | **0/4** (ค้าง 100 หรือขึ้น 0) | 4/4 |

## สิ่งที่แก้

### 1. Host ทิ้งแพ็กเก็ตของเตียงที่ไหลเร็วเกิน 3000 mL/h (ทั้งสาม Host)

Host ปฏิเสธแพ็กเก็ตที่อัตราไหลเกิน `MAX_PLAUSIBLE_RATE_HR` = 3000 (เพิ่มใน 4.8.0-OLED
เพื่อกันแพ็กเก็ตขยะ) แต่ Station นับหยดที่ห่างกันได้ถึง 55 ms (C3 60 ms) ซึ่งกับชุด DF10
คำนวณได้ถึง 3600000 / (55 x 10) = **6545 mL/h**

ตอนไหลอิสระด้วยชุด DF10 ซึ่งเป็นเหตุที่ต้องเตือนที่สุด Host จึงทิ้งแพ็กเก็ตทุกใบ ผลคือ

* Host ขึ้น OFFLINE แล้ว LOST หลังราว 35 ถึง 38 วินาที (ตามเกณฑ์ OFFLINE ของแต่ละรุ่น) **แทน TOO FAST**
* เครื่องประจำเตียงขึ้น ONE-WAY และไม่มีรหัสเตือนใด ๆ เพราะ Host ไม่ได้ยินมันแล้ว

แก้เป็น 7000 mL/h สูงกว่าค่าที่ Station ทุกสายส่งได้จริง แต่ยังกันแพ็กเก็ตขยะ (ค่าติดลบ NaN หรือค่าหลักแสน) ได้เหมือนเดิม
Host-OLED 4.9.2 · Host-TFT28 4.9.2 · Host-Touch24 4.10.2

### 2. บอร์ดเล็กบูตใหม่แล้วยอดหยดถูกล้าง (Station-C3-OLED)

Host เก็บ `resetSeq` ลง NVS ทุกครั้งที่กด "เริ่มถุงใหม่" ค่าจึงไม่ใช่ 0 อีกเลยหลังใช้ครั้งแรก
C3 เริ่ม `lastResetSeq` ที่ 0 ตอนบูต Sync ใบแรกหลังบูตจึงสั่งรีเซ็ตทุกครั้ง ล้างยอดที่เพิ่งกู้คืน
จาก RTC / NVS (ความสามารถที่เพิ่มในรุ่น 18 เพื่อให้ยอดรอดไฟดับ) ทิ้งไป

สายหลักกับสายเสถียรไม่มีปัญหานี้ เพราะเริ่มที่ -1 แล้วรับค่าแรกไว้โดยไม่รีเซ็ต
C3 1.3.2 ทำแบบเดียวกัน และย้ายการรีเซ็ต (ซึ่งเขียน NVS และส่งเสียง) ออกจากคอลแบ็กของ ESP-NOW
ไปทำใน `loop()` แบบสายหลัก เปลี่ยนเลขเตียงแล้วรับ `resetSeq` ของเตียงใหม่โดยไม่รีเซ็ต
และ `msSinceLastDrop` ส่งอย่างน้อย 1 เมื่อมีหยดแล้ว

## ความต่างที่ยังเหลือ (ไม่กระทบความเข้ากันได้ ไม่ได้แก้ในรอบนี้)

| เรื่อง | รายละเอียด | ข้อเสนอ |
|---|---|---|
| Host-TFT28 ตัดสิน OFFLINE เร็วกว่า | `ONLINE_TIMEOUT_MS` 5 วินาที Host อีกสองรุ่นเป็น 8 วินาทีตั้งแต่แก้อาการ OFFLINE เมื่อมีหลายเตียง | ปรับเป็น 8 วินาที |
| Host-TFT28 ส่ง Sync แบบยิงรวด | ส่งทุกเตียงรวดเดียวพร้อม `delay()` Host อีกสองรุ่นกระจายเป็นช่องเวลา (`sendSyncForStation()`) | พอร์ตวิธีกระจายช่องเวลา |
| Host-TFT28 ไม่มีเตือน NO SIGNAL | เตือนเมื่อเซนเซอร์ไม่เคยเห็นหยดเลย 90 วินาที มีเฉพาะ OLED และ Touch | พอร์ตมา |
| `tools/host-rx-test` ใช้กับ TFT28 ไม่ได้ | เพราะ TFT28 ไม่มี `sendSyncForStation()` ชุดตรวจจึงรันเฉพาะ Host-OLED | ได้เองหลังพอร์ตข้อบน |
| C3 ไม่ใช้ `hostChannel` | เมื่อเราเตอร์เปลี่ยนช่อง C3 กลับมาได้ด้วยการไล่หาช่อง (ช้าสุด 32.5 วินาที) สายหลักย้ายตามทันที | ยอมรับได้ |
