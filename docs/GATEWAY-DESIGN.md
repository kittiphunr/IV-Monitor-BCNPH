# สถาปัตยกรรม Host-Gateway + พีซี

เอกสารนี้อธิบายว่าทำไมจึงแตกสายใหม่ออกจาก Host-OLED และสายใหม่ทำงานอย่างไร
รายละเอียดข้อความที่ส่งระหว่างเครื่องอยู่ที่ [`GATEWAY-PROTOCOL.md`](GATEWAY-PROTOCOL.md)

## 1. ปัญหา

Host-OLED ทำห้าอย่างบนชิป ESP32 ตัวเดียวและวิทยุตัวเดียว

| งาน | ฝั่ง | ภาระ |
|---|---|---|
| รับ ESP-NOW จากเตียง | เตียง | เบา เตียงละ 23 ไบต์วินาทีละใบ |
| ตัดสินเตือน ส่ง Sync กลับ | เตียง | เบา |
| จอ OLED และเสียง | หน้างาน | ปานกลาง (I2C ต่อเฟรม) |
| เว็บเซิร์ฟเวอร์ ตอบ `/api/data` | **ผู้ใช้** | **หนัก** สร้าง JSON ราว 3 KB ด้วย `String` ต่อกันทีละชิ้น ต่อหนึ่งแท็บต่อหนึ่งวินาที |
| Access Point, ล็อกรายนาที, CSV | **ผู้ใช้** | **หนัก** beacon และบัฟเฟอร์ต่อเครื่อง, RAM 2.7 KB ต่อเตียงสำหรับล็อก |

ภาระส่วนใหญ่มาจากฝั่งผู้ใช้ ไม่ใช่ฝั่งเตียง รุ่น 4.7.6 บรรเทาด้วยการยืดจังหวะ poll ตามจำนวนผู้ใช้
ซึ่งยังเป็นการแบ่งเวลาบนชิปตัวเดิม งานไม่ได้หายไป

## 2. แนวทางที่ใช้

ย้ายงานฝั่งผู้ใช้ทั้งหมดไปพีซี Host เหลือสี่งาน

```
 เตียง 1..8                       Host-Gateway                         พีซี
 ┌────────┐   ESP-NOW (23 B/วิ)   ┌────────────────────────┐  HTTP POST  ┌──────────────────────┐
 │Station │ ───────────────────▶ │ รับ → ตัดสินเตือน        │ ─────────▶ │ server.py            │
 │        │ ◀─────────────────── │ จอ OLED + เสียง          │  วินาทีละ 1  │  SQLite (ล็อก/CSV)    │
 └────────┘   Sync (20 B/วิ)      │ ส่งสถานะ (เธรดแยก)       │ ◀───────── │  Dashboard (หน้าเดิม) │
                                  └────────────────────────┘ T + คำสั่ง   └──────────────────────┘
                                        ▲ ไม่มีเว็บเซิร์ฟเวอร์                 ▲ พยาบาลเปิดที่นี่
```

### สิ่งที่ตัดออกจาก Host
- `WebServer` ในโหมดปกติ (เหลือเฉพาะหน้าตั้งค่าครั้งแรก) ไม่มี REST API ไม่มี Dashboard ไม่มี CSV
- Access Point สำรอง เครื่องไม่ต้องดูแลมือถือ
- `LogEntry[60]` ต่อเตียง ย้ายไปฐานข้อมูลที่พีซี
- การสร้าง JSON ตามจังหวะที่ผู้ใช้เรียก เหลือวินาทีละก้อนเดียวไม่ว่ามีกี่คนดู

### สิ่งที่ยังอยู่ที่ Host โดยตั้งใจ
- **การตัดสินเตือนทั้งหมด** พีซีไม่อยู่ในวงจรความปลอดภัย พีซีดับ เราเตอร์ล่ม หรือสายหลุด
  จอและเสียงที่หน้างานทำงานครบเหมือนเดิม
- **ค่าตั้งเตียงใน NVS** Host ตัดสินเตือนได้เองแม้พีซีหาย และพีซีเรียนรู้ค่ากลับจาก Host ได้เมื่อรีสตาร์ต
  จึงไม่มีที่ไหนเป็นต้นฉบับเพียงที่เดียวที่ถ้าพังแล้วค่าหาย

### เธรดแยกบน Host
งานส่งขึ้นพีซีอยู่ใน FreeRTOS task ปักที่คอร์ 0 `loop()` ไม่เคยรอมัน
เธรดนั้นคัดลอกสถานะใต้ล็อกสั้น ๆ แล้วสร้างข้อความนอกล็อก ทุกขั้นเครือข่ายมี timeout
(ต่อ 1.2 วินาที ตอบ 1.5 วินาที) พีซีค้างจึงทำให้เธรดนั้นช้าได้ แต่ไม่ทำให้การรับ ESP-NOW หรือจอสะดุด

## 3. รูปแบบความล้มเหลวและพฤติกรรม

| เหตุการณ์ | ที่ Host | ที่พีซี / หน้าเว็บ |
|---|---|---|
| พีซีดับ | จอขึ้น `PC LINK DOWN` เตือนหน้างานปกติ เปลี่ยนค่าเตียงจากเว็บไม่ได้ | – |
| เราเตอร์ล่ม | จอขึ้น `NO ROUTER` ลองต่อใหม่ถี่ 10 วิ แล้วเว้นห่างขึ้นเท่าตัวถึง 5 นาที เตือนหน้างานปกติ | แถบแดง "พีซีไม่ได้รับข้อมูลจาก Host" ทุกเตียงขึ้นออฟไลน์ ไม่โชว์ตัวเลขเก่าเหมือนปกติ |
| Host ดับ | – | เหมือนเราเตอร์ล่ม |
| ลิงก์ขาดกลางทางตอนสั่งงาน | คำสั่งมีเลขลำดับ พีซีส่งซ้ำจนกว่าจะได้ ack | คำสั่งค้างไม่เกิน 10 นาทีแล้วทิ้ง (กันคำสั่งเก่าไปทำงานข้ามคืน) |
| พีซีรีสตาร์ต | ไม่รู้สึก | เลขลำดับตามไปที่ ack ของ Host คำสั่งใหม่ไม่ถูกข้าม ค่าเตียงเรียนรู้กลับจาก Host ภายในวินาทีแรก |
| Host รีบูต | จำค่าเตียงจาก NVS ได้ | ตัวนับหยดเริ่มใหม่ พีซีนับ "ตัวนับลดลง" เป็นรีเซ็ตแบบเดียวกับที่ Host เดิมทำ |

พีซีไม่เขียนบันทึกรายนาทีขณะ Host เงียบ ช่องว่างในกราฟคือความจริง ไม่มีการแต่งตัวเลขอุดช่อง

## 4. ข้อจำกัดที่รู้อยู่และยังไม่ได้แก้

1. **จำนวนเตียงยังเป็น 8 ต่อ Host** รุ่นนี้ไม่แตะ Station และผังจอ OLED ผังจอปัจจุบันแบ่งเป็นกริดสองคอลัมน์ ไม่พอสำหรับ 16 เตียง
   ฝั่งพีซีและโปรโตคอลรองรับหลาย Host แล้ว (ฟิลด์ `host`, ตัวเลือก Host ในหน้าเว็บ)
2. **หลาย Host ในรัศมีวิทยุเดียวกันทำไม่ได้ทันที** Station ไล่หา Host ตามช่องสัญญาณและแยกด้วยเลขเตียงเท่านั้น
   สอง Host ที่ได้ยิน Station ชุดเดียวกันจะแย่งกัน ต้องเพิ่มการจับคู่ Station↔Host ในเฟิร์มแวร์ Station ก่อน (งานแยก)
3. **ขณะเราเตอร์ล่ม** การค้นหาเราเตอร์ของ `WiFi.begin()` ทำให้วิทยุกระโดดช่อง แพ็กเก็ตจากเตียงอาจหายระหว่างนั้น
   จึงใช้ backoff เว้นห่างขึ้นเท่าตัวเพื่อให้กระทบน้อยที่สุด ผลจริงต้องวัดบนบอร์ด ซึ่งยังไม่ได้ทำ
4. **เครือข่ายเป็น HTTP ธรรมดา** ใช้ในเครือข่ายภายในของหอผู้ป่วย รหัสเกตเวย์กันแค่การส่งผิดที่ ไม่ใช่การเข้ารหัส
   ข้อมูลที่ผ่านทางมีชื่อผู้ป่วย ควรอยู่ใน VLAN/เครือข่ายของหน่วยงานเท่านั้น และตั้ง `--auth` ที่พีซีเสมอ
5. **ยังไม่ได้ทดสอบบนฮาร์ดแวร์จริง** ทุกอย่างตรวจด้วยตัวจำลองบน PC ตามที่ระบุไว้ใน README ของทุกรุ่น

## 5. การตัดสินใจที่ถกกันแล้ว

| ทางเลือก | ตัดสินใจ | เหตุผล |
|---|---|---|
| ให้ Station ส่งผ่านเราเตอร์ตรง (แทน ESP-NOW) | ไม่ทำ | เตียงต้องต่อ Wi-Fi ใช้ไฟมากขึ้น เราเตอร์ล่มแล้วเตียงเงียบ แตะ Protocol v3 ที่ล็อกไว้ |
| MQTT แทน HTTP | ไม่ทำ | ต้องมี broker เพิ่มอีกตัว HTTP + คำตอบพ่วงคำสั่งใช้เครื่องเดียว ไม่ต้องให้ Host รับการเชื่อมต่อขาเข้า |
| JSON ลง (พีซี → Host) | ไม่ทำ | ต้องใช้ ArduinoJson เพิ่มหรือเขียนตัวแกะเอง ข้อความบรรทัดละคำสั่งแกะได้ในไม่กี่สิบบรรทัดและทดสอบง่ายกว่า |
| ให้ Host ถือล็อกไว้ แล้วพีซีมาดึง | ไม่ทำ | ภาระหน่วยความจำและการเรียกขาเข้ากลับมาที่ Host อีกครั้ง |
| Python มาตรฐานเท่านั้นที่พีซี | ใช้ | ติดตั้งบนพีซีโรงพยาบาลได้โดยไม่ต้อง pip ผ่านนโยบายเครือข่าย |
